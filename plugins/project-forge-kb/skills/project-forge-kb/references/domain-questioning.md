# 领域建模访谈

仅在当前领域的代码和已选归档资料调查完成后使用。调查负责提供事实、术语候选和 ADR 问题候选；正式术语与 ADR 必须通过本访谈确认后才能生成。

## 建立设计树

主 Agent 将证据组织为一棵设计树，至少包含两个分支：

- 领域语言：候选词的准确含义、概念边界、易混淆词和应避免的别名；
- 设计决策：反直觉、高风险、难以逆转、容易被未来维护者误改或缺少历史原因的设计。

使用具体业务场景检验术语和设计边界。一个问题依赖的事实或决定是它的父节点；父节点未解决时，不得猜测下游答案。

环境中可以查明的事实由 Agent 或只读子代理调查，不询问用户。调查未完成只会暂时阻塞依赖该事实的分支，其他已就绪问题继续进入当前轮。

## 按 frontier 分轮追问

`frontier` 是前置条件已经明确、当前可以由用户判断的全部问题。每轮提出完整 frontier，逐项编号，说明当前证据并给出推荐答案：

```md
❓ **Q1 - <问题标题>**：<需要用户判断的领域含义或设计原因；必要时给出互斥选项和具体场景。>

当前证据：<代码锚点、归档资料和冲突；不粘贴大段源码。>

➡️ 推荐答案：<基于当前证据的建议，不把推断表述为事实。>
```

等待用户回答后重新计算整棵设计树：已解决节点可能展开新的下游问题，原有假设也可能被推翻。互不依赖的问题放在同一轮；依赖本轮答案的问题留到下一轮。提问不设固定轮数，不以减少对话次数为目标。

人工无法解释的问题结束对应分支并写入 `.review/<domain_id>/domain-questions.md`，不得用 Agent 推断补齐，也不阻塞其他分支。

## 术语准入

候选必须同时满足以下条件，才能写入 L1“术语”：

1. 是这个项目领域中特有的概念，而不是通用编程或框架概念；
2. 开发人员需要对它形成统一理解；
3. 含义已经通过本次访谈明确；
4. 能用一到两句话说明“它是什么”，而不是描述代码如何实现；
5. 存在易混淆说法时，明确应避免的别名和必要的概念边界。

类名、方法签名、字段列表、框架 API、Schema 生成方式和调用链只能作为证据或代码锚点，不能直接充当术语定义。例如，`ToolsDefinition` 的字段清单不是“工具”的定义；应先追问“工具”在本领域准确指什么，再用领域语言定义。

术语一经用户回答确认且满足准入条件，立即写入 L1 草稿。不要等到访谈结束后从代码说明批量生成术语。

## ADR 准入

代码中发现特殊设计时，先追问真实原因、当时考虑的替代方案、变更代价以及未来读者可能产生的误解。只有同时满足以下条件才创建 ADR：

1. 人工确认了真实原因；
2. 存在真正的替代方案和取舍；
3. 设计难以逆转或变更成本较高；
4. 没有背景时，未来维护者很可能误解；
5. 该原因对未来维护仍有价值。

任一条件不满足都不创建 ADR。普通实现事实、显而易见的选择、容易撤销的选择以及 Agent 推测的原因不属于 ADR。

满足准入条件后立即使用 `<skill-dir>/assets/ADR.md` 创建 ADR，并在 L1“设计与决策”中加入摘要和链接。ADR 不设置 `status`；每个领域从 `0001` 起按已有文件递增编号。新决定改变旧决定时创建新 ADR 并说明取代关系，不改写旧 ADR。

## 完成访谈

frontier 为空时，汇总已经写入的术语、规则、边界和 ADR，以及 `.review` 中无法确认的问题，询问用户是否已经达到共同理解。只有用户明确确认后，领域建模访谈才完成，才能登记 `domain-knowledge` 阶段。
