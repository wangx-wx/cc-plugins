# 领域澄清与 ADR

仅在代码和已选归档资料的事实调查完成后使用。目标是让人工解释代码和文档无法证明的领域含义与原始设计考虑，不是让人工重复提供可检索事实。

## 建立设计树

主 Agent 根据证据建立内部设计树，至少检查：

- 同一个词在人工表述、代码和文档中是否含义冲突；
- 模糊或过载词是否需要一个规范术语，哪些别名应避免；
- 领域负责和不负责什么，跨领域的数据、状态和操作由谁拥有；
- 观察到的代码行为是否真的是业务规则，规则有哪些适用范围和例外；
- 取消、重试、重复请求、部分成功和异常状态等具体场景是否暴露边界矛盾；
- 是否存在反直觉、高风险、容易误用或缺少历史原因的设计。

每个决策节点依赖的前置问题构成它的父节点。只有前置条件已经确定的问题才能进入当前 `frontier`。

## 分轮追问

每轮一次提出当前 frontier 的全部问题，逐项编号，并给出证据充分的推荐答案：

```md
❓ **Q1 - <问题标题>**：<只能由人工判断或解释的问题>

当前证据：<代码锚点、归档资料和冲突；不粘贴大段源码。>

➡️ 推荐答案：<Agent 基于证据建议的领域解释或决策。>
```

提出一轮后等待人工回答，再重新计算 frontier。依赖本轮答案的问题留到下一轮。为减少人工介入：

- 可检索事实必须派发子代理调查，不能询问用户；
- 没有实际影响的枝节不进入设计树；
- 多个互不依赖的问题必须合并到同一轮；
- 只有影响 L1 正确性或值得长期保留的设计原因才继续追问；
- 人工明确表示无法解释的问题标记为未解决，不再阻塞其下游之外的其他分支；
- frontier 为空时，集中总结拟写入的术语、规则、边界、ADR 和 `.review` 问题，并请求一次整体确认。确认后才写入文件，不再增加第二次领域审核。

## 结果归位

- 人工确认的概念含义、首选名称和应避免别名写入 L1“术语”。
- 人工确认的业务约束、状态含义、适用范围和例外写入“已确认规则与不变量”。
- 人工确认的领域职责和所有权写入“领域边界”或“相关领域”。
- 无法确认的问题写入 `.review/<domain_id>/domain-questions.md`，不得写入正式 L1，但不阻塞其他内容。

## ADR 准入与写法

发现模糊、不安全、反直觉、容易误用、涉及领域所有权或缺少历史原因的设计时，追问最初的设计考虑。只有同时满足以下两点才使用 `assets/ADR.md` 创建 ADR：

1. 人工已经确认其原因，不能用 Agent 推断代替；
2. 该原因对未来维护或变更判断有长期价值。

人工回答“没有特殊原因”或无法确认时不创建 ADR。ADR 记录已经确认的设计及原因，不记录调查状态，不设置 `status`。每个领域从 `0001` 起按已有文件递增编号；新决策改变旧决策时创建新 ADR，并在正文中说明取代关系，不改写旧 ADR。
