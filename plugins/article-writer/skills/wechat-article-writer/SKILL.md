# 公众号文章写作

把零散素材变成一篇有故事感、有画面感的科技领域公众号文章。

## 核心原则:为什么是"讲故事"

技术文章最大的敌人是"信息密度高,读者没动力读完"。同样讲一个 Transformer,「2017 年 Google 发表的论文 Attention Is All You Need」是教科书写法;「2017 年夏天,Google Brain 的会议室里,Ashish Vaswani 在白板上画下一张图,这张图后来颠覆了 AI 的走向」是公众号写法。两种写法都没有错,但后者读者愿意继续往下滑。

讲故事不等于编故事——技术、数据、引用必须真实。讲故事是指**用具体的场景、人物、动作、感官细节代替抽象的概念陈述**。

## 工作流程:分四步走,不要一次成文

**用户明确要求分步处理。** 不要拿到素材就直接给一篇 5000 字的成稿——大概率方向就跑偏了,改起来很痛苦。按下面的节奏来:

### 第 1 步:消化素材(自己做,不打扰用户)

读完用户给的所有素材。如果是 PDF/Word,用 Read 工具读完;如果是链接,用 WebFetch 抓内容;如果是几段散乱的笔记,通读一遍找内在关联。

完成后,用 2-3 句话向用户回放你抓到的核心信息,确认理解没跑偏。例如:

> 我看完了。素材里主要讲了三件事:(1) Anthropic 在 11 月发布了 Claude 4.7;(2) 它的核心改进是上下文压缩;(3) 你个人测试了一个长代码库 review 的场景。我打算从你这个亲测体验切入——对吗?

如果素材明显不够(只有一句话的标题、或者素材里没有具体细节),直接告诉用户哪里需要补充,不要硬编。

### 第 2 步:提选题角度(给用户选)

同一份素材,角度不一样,文章完全是两篇。**给用户 2-3 个角度选**,而不是直接定一个。每个角度说明:

- **切入点**:从什么场景/人物/事件起笔
- **主线**:整篇文章要回答的核心问题
- **适合读者**:谁会觉得这篇有用
- **预估长度**:短中长

例如(同样是「Claude 4.7 发布」这个素材):

> **角度 A:亲历者视角**——从你某天用 Claude 4.7 review 那个 8 万行代码库的具体瞬间起笔,主线是"AI Coding 工具进化到什么程度了",中篇约 3500 字,适合开发者读者。
>
> **角度 B:行业观察**——从 OpenAI、Google、Anthropic 三家近半年模型节奏的对比起笔,主线是"为什么 Anthropic 这次选择押注长上下文",长文约 5000 字,适合关心 AI 行业格局的读者。
>
> **角度 C:工具横评**——从 Cursor / Claude Code / Copilot 的对比起笔,主线是"4.7 时代哪个 AI Coding 工具最值得用",中篇约 3000 字,适合在选工具的程序员。
>
> 你想往哪个方向走?也可以告诉我新角度。

### 第 3 步:出大纲(确认后再写正文)

角度定了之后,出一个**带血肉的大纲**——不是干巴巴的「一、引言;二、正文;三、结尾」,而是把每个小节的标题、要讲什么、用什么细节都列出来。结构参考:

```
开头钩子(约 300 字)
  场景:[具体的人/时间/地点/动作]
  矛盾/反差:[让读者好奇的点]
  抛出问题:[本文要回答什么]

【小标题 1:动词或反差句,不要平铺】(约 800 字)
  - 要讲的核心论点
  - 用到的素材/数据
  - 关键细节、引用、类比

【小标题 2:...】(约 800 字)
  ...

【小标题 N】(约 800 字)
  ...

结尾(约 400 字)
  收回开头的钩子
  抛出一个让读者带走的问题/判断/金句
```

把大纲给用户看,等用户确认或调整再进入第 4 步。**不要跳过这一步。**

### 第 4 步:写正文

按大纲扩写。写之前请先翻一遍 [references/storytelling-techniques.md](references/storytelling-techniques.md)、[references/opening-patterns.md](references/opening-patterns.md)、[references/ending-patterns.md](references/ending-patterns.md)、[references/anti-patterns.md](references/anti-patterns.md)。这几个文件是这个 skill 的灵魂——主文件只讲流程,具体怎么写好,在子文件里。

输出格式:
- 直接输出 Markdown,标题用 `##` 二级标题(公众号编辑器对二级标题渲染最自然)
- 段落之间空一行
- 关键句子可以单独成段(增加节奏感)
- 引用用 `> ` 表示
- 在需要配图的位置插入提示:`[配图建议:xxx]`,例如 `[配图建议:Claude 4.7 的截图]`、`[配图建议:Transformer 论文截图]`
- 不要写"今天我们来聊一聊"、"话不多说,直接开始"这种废话开场

## 长度的判断

用户没给定长度。按下面的规则自己定:

- **素材稀薄**(几句话的想法 + 一两个数据点):短文 1500-2500 字,把核心讲清楚,不要硬撑
- **素材中等**(一份完整的笔记 / 一个事件的多个角度):中篇 3000-5000 字
- **素材丰厚**(完整研究报告 / 多份长文档 / 多个采访)：长文 5000-8000+ 字

宁可短而紧,不要长而水。读者退订一个公众号的常见理由是「越写越水」。

## 关于「画面感」的反复强调

"画面感"是这个 skill 的核心 DNA,但它最容易在写的过程中被遗忘。写完一段如果发现自己在写「Transformer 是一种基于注意力机制的神经网络架构」,停下来,问自己:**我能不能换一种说法,让读者脑子里浮现出一幅画**?例如把上面这句改成:

> Transformer 抛弃了之前所有「一个词一个词读」的笨办法,让模型像一个会同时看全篇的速读高手——它一眼扫过去,就知道哪个词跟哪个词有关。

注意:技术细节没丢,但读者眼前有画面了。

## 反复迭代的提示

正文写完后,把成稿交给用户。**不要自己反复"打磨"占用过多时间。**用户读完后给反馈,你再针对性地改某一段、某一节——而不是整篇重写。改的时候只动用户提到的部分,别顺手改别的——参见 CLAUDE.md 里"Surgical Changes"的要求。
